# Phase 0 architecture decision

Date: 2026-10-17. Direction authorized by the user's request to start Phase 0.

## Decision

Use Unity 6000.3.26f1 LTS, C#, and URP in a separate `android-game/` project. The existing static site and Node server continue as the browser baseline. This phase adds no backend, purchase SDK, analytics service, or account system.

The package manifest pins URP 17.3.0 and uGUI 2.0.0, both confirmed in the installed Editor's bundled package manifests. Editor import is the authoritative package-resolution check; the public registry listing does not establish availability of Editor-bundled packages. Record the resolved lockfile and any justified version adjustment after import. Unity licensing must be activated by the user; commercial eligibility is not assumed.

## Boundaries

- `ProbeSimulation` owns fixed-step position, heading, cooldown, and boundary state. It has no Unity references.
- `ArenaProbe` adapts input and renders state; it does not use Rigidbody physics to decide gameplay movement.
- The probe runs at 120 simulation steps per second, with rendering targeting 60 or 30 FPS. Input and gameplay timing must remain independent of render rate.
- uGUI supplies safe-area-aware touch controls. Legacy Unity input is sufficient for the probe; moving to the Input System later requires an explicit input migration and multi-touch/controller checks.
- URP settings and a scene are generated by an explicit Editor command, then become ordinary editable Unity assets. They are not regenerated every launch.
- Scene creation is idempotent and uses persisted material references to avoid stripping required runtime shaders.
- Versioned persistent progress, purchases, and network protocol handling belong to later phases.

## Rendering baseline

Use an unlit stylized arena with 2x MSAA, HDR disabled, no depth/opaque copy, no real-time shadows, and 0.85 render scale. This establishes a simple mobile baseline; it is not the final commercial art direction or a claim of performance. The first scene has a procedural cycle, luminous grid and boundaries, and a steady following camera.

Phase 1 should replace prototype geometry with authored models and improve lighting/effects within measured budgets. Add quality presets based on physical-phone evidence. Do not use expensive effects solely because the engine supports them.

## Android identity and data

`com.gridrun.prototype` and `Grid Run - Phase 0` are development identifiers only. ARM64 IL2CPP and OpenGL ES 3 are the first build configuration. API 29 is a provisional compatibility floor; API 36 is an explicit build target, not a permanent store-policy claim. Landscape supports both left and right rotation and respects display cutouts.

There is no gameplay telemetry or player data transmission in this probe. Device evidence is local and ignored. Use debug signing only; a production key and final app identity are separate release decisions.

## Migration and later multiplayer

Port behavior from the browser by explicit parity checks. Do not claim cross-play from similar-looking movement. At Phase 2, test a Unity client against the existing Node service and compare that with a C# authoritative server sharing the simulation. Choose based on latency, maintainability, and measured resource use before adding providers.

## Assets and ownership

Phase 0 visuals are procedural project code plus Unity-provided fonts/shaders. No external art, music, or purchased assets are introduced. Future assets need recorded provenance and redistribution rights. Public branding remains a release decision.

## Known limitations

This is a movement probe, not a complete game. It has no trails, AI, weapons, scoring, save data, online play, or shop. The generated scene and configuration still require Editor import, compilation, visual review, and Android device verification. A source-only review cannot satisfy those gates.
